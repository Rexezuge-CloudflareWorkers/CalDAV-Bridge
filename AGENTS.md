# AGENTS.md

Guidance for agents working in CalDAV Bridge.

## Overview

CalDAV Bridge is a Cloudflare Worker API with a Vite React management UI. It connects Google Calendar and Microsoft Outlook Calendar over OAuth2 and exposes them through read/write CalDAV endpoints.

## Commands

Always source the user's toolchain setup before Node, pnpm, npm, npx, or Wrangler commands:

```bash
source ~/.customrc
volta run pnpm install
volta run pnpm run typecheck
volta run pnpm run test
volta run pnpm run test:integration
volta run pnpm run build
volta run pnpm run typegen
```

## Architecture

**API app** (`apps/api/`):

- `src/index.ts` — exports the default `fetch`/`scheduled` handlers via `CalDavBridgeWorker`; re-exports `CronTasksWorker` and `OAuth2TokenRefreshWorker` from `@caldav-bridge/background` for DO bindings.
- `src/workers/CalDavBridgeWorker.ts` — thin Hono router (extends the kit's `AbstractEntrypointWorker`): registers `/user/*`, `/api/oauth2/callback/:applicationId`, `/dav/*`, and the SPA fallback; all handler logic lives in `@caldav-bridge/backend-services`. DAV XML dispatch stays here; only pure CalDAV helpers live in services.
- `src/middleware/` — `MiddlewareHandlers.userAuthentication()` (Cloudflare Access JWT via `EmailValidationUtil` + `UserService.upsertUser`), setting `AuthenticatedUser` to the resolved `UserIdentity` and mapping client errors to `{ error }` JSON.
- `src/generated/spa-shell.ts` — generated by web build; do not edit.

**Background app** (`apps/background/`):

- `CronTasksWorker.ts` — DO serializing cron runs (`POST /run`, `already_running` dedupe) → `DatabaseCleanupTask`.
- `OAuth2TokenRefreshWorker.ts` — DO for token refresh and auth-code exchange (`blockConcurrencyWhile`).
- `scheduled/` — `IScheduledTask` + `DatabaseCleanupTask` (draft/orphan apps, sessions, credentials, tombstones, empty users).

**Packages**:

- `shared/` — cross-package constants, models, schemas, utils (`BaseUrlUtil`, `CalDavCredentialUtil`, `RetryAfterError`).
- `backend-runtime/` — `ConfigurationManager` (static namespace; add new env vars via namespace groups, not inline — `EnvParser` is the kit's); `http/` response helpers (`jsonResponse`, `errorResponse` mapping a `ServiceError` → `{ error }`); DO naming constants.
- `backend-data/` — all D1 access via DAOs (`ConnectedApplicationDAO`, `CalDavCredentialDAO`, `CalendarObjectMappingDAO`, `OAuth2AuthorizationSessionDAO`, `UserDAO`, `UserEmailDAO`) on the kit's `BaseDAO` and the repo's `EncryptedDAO`; utils `D1SessionUtil` (`createD1SessionEnv`).
- `provider-clients/` — `calendar/` (`CalendarProviderUtil` facade dispatching on provider id + `GoogleCalendarProviderUtil`/`OutlookCalendarProviderUtil` + shared HTTP/retry in `BaseCalendarHttp`), `oauth2/` (`OAuth2ProviderUtil`). New provider behavior → per-provider util behind the facade, not branch on provider id in callers.
- `backend-services/` — business logic by domain: `application/` (`ApplicationService`), `auth/` (`EmailValidationUtil`), `calendar/` (`CalendarService`, `CalDavUtil`, `ICalendarUtil`), `credential/` (`CredentialService`), `oauth2/` (`OAuth2AuthorizationService`, `OAuth2AccessTokenService`, `OAuth2StateUtil`), `user/` (`UserService`, `UserIdentityService`).

**Other**: `migrations/` (latest: `0004_decouple_user_identity.sql`), `functions/[[path]].ts` (Pages → API Worker proxy), `test/` (Vitest suites: `dao/`, `helpers/`, `middleware/`, `ops/`, `schema/`, `security/`, `services/`, `tasks/`, `utils/`, `web/`, `workers/`), `test/integration/` (its own config: worker + real DAOs against `node:sqlite` with the migrations applied). Aliases, coverage rules and thresholds live in `vitest.shared.mts`, imported by `vitest.config.mts` and `test/integration/vitest.config.mts`.

## The Kit (`@rexezuge/*`)

The framework kernel is **not in this repo**. It lives in `Rexezuge-CloudflareWorkers/SDK` and is consumed as a normal dependency:

| Kit package | Replaces what this repo used to carry |
| --- | --- |
| `@rexezuge/errors` | the whole `backend-errors` package |
| `@rexezuge/runtime` | `backend-runtime/base/*`, `EnvParser` |
| `@rexezuge/shared` | `shared/utils/{CryptoUtil,TimestampUtil,UUIDUtil}.ts` |
| `@rexezuge/d1` | `backend-data/{dao/BaseDAO, utils/D1Utils, utils/D1ErrorClassifier, crypto/aes-gcm}` |

Kit APIs this repo has adapted to:

- **Errors** are the kit taxonomy: `error.status` / `error.type` / `error.retryable` / `error.expose` / `ServiceError.from(value)` — there are no `getErrorCode()`/`getErrorMessage()` getters. The kit carries no transport headers, so the one case that needs one throws `RetryAfterError` (in `shared/`), and `errorResponse`/`safeDav` read `error.headers` off that class only.
- **BaseDAO is sql-first**: `run(sql, bindings)`, `first<T>(sql, bindings)` (absence is `undefined`, not `null`), `all<T>(sql, bindings)`, `count`, `batch(statements)`. DAOs state their SQL directly; there is no closure wrapper.
- **AES-GCM** is `encryptSecret(plaintext, key)` / `decryptSecret({ ciphertext, iv }, key)` with the kit's envelope, and the key must be **base64 of exactly 32 bytes** (`AES_ENCRYPTION_KEY`), enforced fail-closed.
- `PayloadTooLargeError` is the 413 class name.

**Dependency wiring.** The kit deps are ordinary published versions (`^1.0.2`), so CI is a plain `pnpm install` — no kit staging. Two things know about kit *HEAD*: the kit's own `consumer-matrix` job re-points this repo's deps at kit HEAD with its `relink-consumer.mjs` and runs these same gates, and a local developer can do the same deliberately:

```bash
node <kit>/scripts/relink-consumer.mjs --kit <kit> --consumer .   # then pnpm install
```

All `@rexezuge/*` deps move together, root devDependencies included. A lockfile that resolves one package at 1.0.1 and another at 1.0.2 loads *two copies* of the taxonomy, and `error instanceof ServiceError` then answers false across the boundary — the service suites fail in ways that look like logic bugs and are not.

**Vitest resolves the kit differently.** The kit ships ESM `dist/` with bundler-style extensionless relative imports (its own tsconfig is `moduleResolution: Bundler`), which Node's ESM resolver refuses; Vitest 4 would externalize those copies and import them with Node, failing on `./BaseDAO` inside `@rexezuge/d1`'s `dist/index.js`. `vitest.shared.mts` therefore lists the kit in `resolve.noExternal`, so the kit runs through Vite's pipeline — the same resolver that bundles the worker and the SPA — and a test loads the very dist the worker ships.

Identity is deliberately **not** adopted from the kit — see **User Identity** below; the kit's canonical `users` table differs from this repo's.

## CI

`.github/` — `actions/setup-env` (pnpm + Node 24 + cached install) and `actions/retry-step` (re-runs a bash command on failure; every wrangler and `gh` call goes through it, since those are the flaky ones). `workflows/`: `continuous-integration.yml` runs `checks` / `unit-tests` / `integration-tests` / `build` in parallel on `main` and PRs, then auto-merges Dependabot PRs and dispatches deployment after an upstream sync; `continuous-deployment.yml` deploys the Worker and Pages only once CI succeeded on `main`; `backup-main.yml` mirrors `main` to Azure DevOps and GitLab, each gated on its secrets being configured; `scheduled-version-update.yml` stamps `.github/.version`; `upstream-sync.yml` merges upstream `main` into a fork.

`scripts/check-god-files.mjs` reports source files over 300/400 lines. It is **advisory** and always exits 0 -- four files are still over the hard limit, so a gate would fail every push until they are split.

## User Identity

Account identity is `users.user_id` (a UUID). An email address is _not_ an identity.

- `users.user_id` — the stable account key. Everything the account owns is keyed on it: `connected_applications.user_id`, and through `application_id`, every CalDAV credential, calendar mapping and OAuth2 session.
- `users.current_email` — the mutable sign-in address, lowercased and unique.
- `users.email` — the **frozen anchor**. Still the PRIMARY KEY, and **never updated**, because `connected_applications` carries a live `FOREIGN KEY (user_email) REFERENCES users(email) ON DELETE CASCADE`. Do not `UPDATE users SET email`. Migration 0004 kept it precisely so that reference could keep resolving without a table rebuild, which D1 does not permit (it honours neither `PRAGMA foreign_keys = off` nor `legacy_alter_table`).
- `user_emails` — the address registry. `is_verified = 1` means the address may sign in; a changed-away-from address is retained with `is_verified = 0` so pre-change rows stay attributable, and is re-pointed (never deleted) when a later account legitimately claims it.

Resolution lives in `UserIdentityService.resolveOrCreate()` and is ordered deliberately: a registered address is authoritative, and a _revoked_ one resolves to nobody while skipping the `users` anchor fallback — otherwise a reassigned address would hand the previous holder's applications to whoever presents it next.

New accounts prefer the real address as their anchor (matching pre-0004 rows) and fall back to `UserDAO.newAnchor()` (`anchor-<hex>@users.invalid`, an RFC 6761 non-deliverable domain) only when the address is already another account's anchor. `UserDAO.insertIfAbsent()` reports whether it actually created the row; reading the anchor back instead would return the previous holder's account.

Changing a user's address is an operator action — `pnpm exec tsx scripts/change-email.ts --db caldav-bridge-db --account <email> --to <new> --dry-run` (`--id`, `--remote`, `--audit`). It claims, moves, then revokes, in that order, and never touches the anchor. There is no self-service route: nothing here can prove control of a new address.

## Import Direction

```
Layer 0: shared                          — zero @caldav-bridge/* deps
Layer 1: backend-runtime                 → layer 0 only
Layer 2: backend-data, provider-clients  → layer 0 only
Layer 3: backend-services                → layers 0–2 (not apps)
Layer 5: apps/background                 → layers 0–3 (provider-clients OK)
         apps/api                        → layers 0–3 + background (NOT provider-clients directly)
```

Enforced by ESLint `no-restricted-imports` in `eslint.config.mjs`. The rules ban `@caldav-bridge/*` specifiers only, so `@rexezuge/*` imports are unrestricted by design: the kit is the shared kernel every layer may stand on (this is how `provider-clients` reaches `RetryAfterError` through `shared`, and how `backend-data` imports the kit's `BaseDAO`).

## Auth And Routing

- `/user/*` — Cloudflare Access (`MiddlewareHandlers.userAuthentication()` verifies the `cf-access-jwt-assertion` header), resolves the address to an account via `UserService.upsertUser`, and sets `AuthenticatedUser` (`UserIdentity`). Handlers authorize on `userId`; `currentEmail` is for display only. See **User Identity**.
- `DEV_AUTH_EMAIL` bypasses Access locally.
- `/api/oauth2/callback/:applicationId` — public; secured by one-time state + PKCE.
- `/dav/*` — public to Cloudflare Access; CalDAV Basic auth with generated CalDAV app passwords (`WWW-Authenticate: Basic` challenge on 401).
- `/user/*` requests participate in D1 sessions (`x-d1-bookmark` round-trip for read-after-write consistency); the web `apiFetch` already sends/stores the bookmark.
