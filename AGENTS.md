# AGENTS.md

Guidance for agents working in CalDAV Bridge.

## Overview

CalDAV Bridge is a Cloudflare Worker API with a Vite React management UI. It connects Google Calendar and Microsoft Outlook Calendar over OAuth2 and exposes them through read/write CalDAV endpoints.

## Commands

Always source the user's toolchain setup before Node, pnpm, npm, npx, or Wrangler commands:

```bash
source ~/.customrc
volta run pnpm install
volta run pnpm run typecheck
volta run pnpm run test

volta run pnpm run typegen
```

## Architecture

**API app** (`apps/api/`):

- `src/index.ts` — exports the default `fetch`/`scheduled` handlers via `CalDavBridgeWorker`; re-exports `CronTasksWorker` and `OAuth2TokenRefreshWorker` from `@caldav-bridge/background` for DO bindings.
- `src/workers/CalDavBridgeWorker.ts` — thin Hono router (extends `AbstractEntrypointWorker`): registers `/user/*`, `/api/oauth2/callback/:applicationId`, `/dav/*`, and the SPA fallback; all handler logic lives in `@caldav-bridge/backend-services`. DAV XML dispatch stays here; only pure CalDAV helpers live in services.
- `src/middleware/` — `MiddlewareHandlers.userAuthentication()` (Cloudflare Access JWT via `EmailValidationUtil` + `UserService.upsertUser`), setting `AuthenticatedUser` to the resolved `UserIdentity` and mapping client errors to `{ error }` JSON.
- `src/generated/spa-shell.ts` — generated by web build; do not edit.

**Background app** (`apps/background/`):

- `CronTasksWorker.ts` — DO serializing cron runs (`POST /run`, `already_running` dedupe) → `DatabaseCleanupTask`.
- `OAuth2TokenRefreshWorker.ts` — DO for token refresh and auth-code exchange (`blockConcurrencyWhile`).
- `scheduled/` — `IScheduledTask` + `DatabaseCleanupTask` (draft/orphan apps, sessions, credentials, tombstones, empty users).

**Packages**:

- `shared/` — cross-package constants, models, schemas, utils (`BaseUrlUtil`, `CalDavCredentialUtil`, `CryptoUtil`, `TimestampUtil`, `UUIDUtil`).
- `backend-errors/` — typed error hierarchy (`ServiceError` with `getErrorCode()`/`getErrorType()`/`getErrorMessage()` plus optional transport `headers`): `BadRequestError`, `UnauthorizedError`, `ForbiddenError`, `NotFoundError`, `MethodNotAllowedError`, `PreconditionFailedError`, `ServiceUnavailableError`, `InternalServerError`, `DatabaseError`.
- `backend-runtime/` — `ConfigurationManager` + `EnvParser` (add new env vars via namespace groups, not inline); abstract worker base classes (`AbstractEntrypointWorker`, `AbstractDurableObjectWorker`); `http/` response helpers (`jsonResponse`, `errorResponse` mapping `ServiceError` → `{ error }`); DO naming constants.
- `backend-data/` — all D1 access via DAOs (`ConnectedApplicationDAO`, `CalDavCredentialDAO`, `CalendarObjectMappingDAO`, `OAuth2AuthorizationSessionDAO`, `UserDAO`, `UserEmailDAO`) on `BaseDAO`/`EncryptedDAO` (`D1Queryable` ctor type); `crypto/` AES-GCM; utils `D1SessionUtil` (`createD1SessionEnv`), `D1Utils` (retry), `D1ErrorClassifier`.
- `provider-clients/` — `calendar/` (`CalendarProviderUtil` facade dispatching on provider id + `GoogleCalendarProviderUtil`/`OutlookCalendarProviderUtil` + shared HTTP/retry in `BaseCalendarHttp`), `oauth2/` (`OAuth2ProviderUtil`). New provider behavior → per-provider util behind the facade, not branch on provider id in callers.
- `backend-services/` — business logic by domain: `application/` (`ApplicationService`), `auth/` (`EmailValidationUtil`), `calendar/` (`CalendarService`, `CalDavUtil`, `ICalendarUtil`), `credential/` (`CredentialService`), `oauth2/` (`OAuth2AuthorizationService`, `OAuth2AccessTokenService`, `OAuth2StateUtil`), `user/` (`UserService`, `UserIdentityService`).

**Other**: `migrations/` (latest: `0004_decouple_user_identity.sql`), `functions/[[path]].ts` (Pages → API Worker proxy), `test/` (Vitest suites: `dao/`, `errors/`, `helpers/`, `middleware/`, `ops/`, `schema/`, `services/`, `tasks/`, `utils/`, `workers/`).

## User Identity

Account identity is `users.user_id` (a UUID). An email address is _not_ an identity.

- `users.user_id` — the stable account key. Everything the account owns is keyed on it: `connected_applications.user_id`, and through `application_id`, every CalDAV credential, calendar mapping and OAuth2 session.
- `users.current_email` — the mutable sign-in address, lowercased and unique.
- `users.email` — the **frozen anchor**. Still the PRIMARY KEY, and **never updated**, because `connected_applications` carries a live `FOREIGN KEY (user_email) REFERENCES users(email) ON DELETE CASCADE`. Do not `UPDATE users SET email`. Migration 0004 kept it precisely so that reference could keep resolving without a table rebuild, which D1 does not permit (it honours neither `PRAGMA foreign_keys = off` nor `legacy_alter_table`).
- `user_emails` — the address registry. `is_verified = 1` means the address may sign in; a changed-away-from address is retained with `is_verified = 0` so pre-change rows stay attributable, and is re-pointed (never deleted) when a later account legitimately claims it.

Resolution lives in `UserIdentityService.resolveOrCreate()` and is ordered deliberately: a registered address is authoritative, and a _revoked_ one resolves to nobody while skipping the `users` anchor fallback — otherwise a reassigned address would hand the previous holder's applications to whoever presents it next.

New accounts prefer the real address as their anchor (matching pre-0004 rows) and fall back to `UserDAO.newAnchor()` (`anchor-<hex>@users.invalid`, an RFC 6761 non-deliverable domain) only when the address is already another account's anchor. `UserDAO.insertIfAbsent()` reports whether it actually created the row; reading the anchor back instead would return the previous holder's account.

Changing a user's address is an operator action — `pnpm exec tsx scripts/change-email.ts --db caldav-bridge-db --account <email> --to <new> --dry-run` (`--id`, `--remote`, `--audit`). It claims, moves, then revokes, in that order, and never touches the anchor. There is no self-service route: nothing here can prove control of a new address.

## Import Direction

```
Layer 0: shared, backend-errors          — zero @caldav-bridge/* deps
Layer 1: backend-runtime                 → layer 0 only
Layer 2: backend-data, provider-clients  → layer 0 only
Layer 3: backend-services                → layers 0–2 (not apps)
Layer 5: apps/background                 → layers 0–3 (provider-clients OK)
         apps/api                        → layers 0–3 + background (NOT provider-clients directly)
```

Enforced by ESLint `no-restricted-imports` in `eslint.config.mjs`.

## Auth And Routing

- `/user/*` — Cloudflare Access (`MiddlewareHandlers.userAuthentication()` verifies the `cf-access-jwt-assertion` header), resolves the address to an account via `UserService.upsertUser`, and sets `AuthenticatedUser` (`UserIdentity`). Handlers authorize on `userId`; `currentEmail` is for display only. See **User Identity**.
- `DEV_AUTH_EMAIL` bypasses Access locally.
- `/api/oauth2/callback/:applicationId` — public; secured by one-time state + PKCE.
- `/dav/*` — public to Cloudflare Access; CalDAV Basic auth with generated CalDAV app passwords (`WWW-Authenticate: Basic` challenge on 401).
- `/user/*` requests participate in D1 sessions (`x-d1-bookmark` round-trip for read-after-write consistency); the web `apiFetch` already sends/stores the bookmark.

## Git Commit Messages

- Use Conventional Commits with this subject format: `<TYPE>[optional scope]: <description>`.
- Write the type in uppercase, for example `FIX`, `FEAT`, `DOCS`, `STYLE`, `REFACTOR`, `TEST`, `BUILD`, `CHORE`.
- Write the optional scope in lowercase inside parentheses, for example `FEAT(runtime): Add Scheduled Job Status`.
- Write the description as concise human-readable words with spaces, capitalizing the first letter of each word.
- When creating a commit from `main`, first switch to a new branch generated from the planned commit subject.
- Use lowercase slash-separated branch names: `type/description` when there is no scope, or `type/scope/description` when there is a scope.
- Convert the description to kebab-case for the branch, for example `docs/latest-agents-context-reflection`.
- Use Markdown for optional commit bodies, separated from the subject by a blank line.
- Use optional footers after the body, separated by a blank line, following git trailer-style formatting.
- Use `FIX` for bug patches and `FEAT` for new features; other conventional types are allowed when they better describe the change.
- Mark breaking API changes with `!` after the type or scope, or with a `BREAKING CHANGE: <description>` footer.

```text
<TYPE>[optional scope]: <description>

[optional body in Markdown]

[optional footer(s)]
```
